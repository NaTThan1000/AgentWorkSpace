# 升级到 1.0.0

前一发行形态：legacy，即各来源仓原有 released。1.0.0 是统一发布仓首版；不存在已发布的统一 0.x 仓库版本。本版不虚构一次前版本发布。未来每版必须声明直接前一版，并验证实际迁移；版本不兼容或需要人工处理时明确列出。

## 新工作区

运行统一 init 计划并应用，按需指定包。meta 始终为完整版；业务包完成框架接入后直接用。Knowledge 空库查询合法，首次 Ingest 才需要实际用途/主题；不要为了安装自动编造个人知识范围。

## 从旧包迁移

1. 保留旧目录和 Git 基线，备份现有会话/知识/项目；停止对同一实例的并行写入。发布仓 upgrades/legacy 中保存原发行包文件摘要与来源身份，不含用户数据。
2. 用本版 init 在一个独立目标目录搭建根，暂不指定待迁移包。不要对旧根 AGENTS 等文件强制覆盖：旧教学组合搭建的个人规则需要 Agent 对照新内核进行语义合并，保留用户明确偏好和原授权；未完成合并就不宣称旧工作区已升级。
3. 由 Agent 将旧包的完整使用副本复制到目标 `modules/brainstorm`、`modules/f2s` 或 `modules/knowledge`，保留原目录不动。复制前检查真实路径与链接；不复制 `.git`、凭据、工具缓存或无关仓库。此复制包含用户需要保留的业务文件，不能只复制框架漏掉数据。
4. `python scripts/workspace.py adopt --target <目标> --packages <包名>` 识别旧 `_release.json` 来源身份并预览归属；确认后加 `--apply`。adopt 只登记旧框架基线，不改正文和用户数据。未知旧版拒绝，按源 Git 取得准确旧发行清单或人工迁移，不冒用已知身份。
5. 运行本版 `upgrade --target <目标>`。框架未修改的部分升级；本地修改若与新版冲突，保留原件，在对照副本解决后重新预览。不能伪造安装状态或清空用户文件来取得 PASS。
6. 核对实际会话继续、Query/Ingest、项目恢复和相关工具；确认目标可用后再决定旧目录如何保留，不由升级器删除原数据。

## 包兼容范围

- Brainstorm：保留会话、原始输入、决定和修订链；已关闭档案只读。新工具对旧活跃 session 的迁移仍按包内合同先预演，不把统一安装当成所有历史 session schema 已验收。
- F2S：保留项目工程、底稿、有效决定和真实验收证据。本版工作流/工具更新不自动重建旧游戏，不把旧已接受范围降级为未接受；引擎兼容由实际项目验证。
- Knowledge：只替换框架，raw/wiki/domain/group 正文和历史运行保留。公开包维护独立便携 framework 2.0 与 Query/Ingest controller v2，不等同于私有宿主最新 consolidated 控制器；16 个运行文件有意保留便携实现，并在来源 manifest 记录适配原因、版本和摘要。历史已批准运行仍按原 schema/批准版本解释，不重新签署旧哈希，不用新格式自动重写历史。首次新消化按现行合同取得范围并审核。
- meta：A–E 功能组合退役，改为唯一完整版；旧个人根规则不在通用自动升级覆盖范围，需要语义合并。空画像/记忆模板不授予写入权限。

## 失败与恢复

初始复制和升级保持原目录可用。统一工具每次应用记录 transaction ID，rollback 默认只预览；应用回滚只恢复该事务框架文件及安装记录，不回退未知用户数据。事务后又改动的文件报告冲突，先保全再人工合并。源 released 的移除可以从来源仓迁移前提交恢复；公开发布 tag 保持不可变。

本版验证区分真实旧发行清单迁移、同版幂等和合成下一版本升级/冲突/恢复。合成未来版只验证机制，不冒充已发布的前一仓库版本；长期业务效果与真人验收不在这些工程结果中。
