# 消化生成与融合实作

这是可重复执行的工作样例，不是额外审批层。下面材料全部为合成测试，不是科研事实；实际业务以完整来源为准。流程分别由 INGEST_PROTOCOL、raw-sources/README、Wiki规则和 RAW_STANDARD_V2 拥有，本文把它们接成能照做的过程。

## 先规划来源全集

先读全部来源，运行 source-content-audit.ps1 -Action manifest；多个 Clipping 全部列入，不只取自认为重要的章节。每单元只有一个 ID 和版本，写作骨架按全部 ID 分配位置。按定义、机制、证据、条件、重复/元信息分工，不先生成覆盖结论。

合成来源：

1. 开头定义：“可读反馈”是玩家能辨认行动结果，并非越亮越好。
2. 步骤：“先确定要识别的事件，再选择通道，在竞争信息场景验证；不能先堆特效再倒推事件。”
3. 测试：“在 60 fps 的同一测试设备，旧方案 6 帧、新方案 3 帧显示命中；只有初次接触的 12 名玩家参加，7 名说更容易辨认。未隔离音效变化。”
4. 后节限定：“如果多目标同时命中，单目标测试不能证明并发信息仍清楚；光敏条件也没有测试。”
5. 图表：另示远近目标遮挡关系，正文没有描述图中位置。
6. 背景：“旧版本以美观为主，直到试玩者把无伤闪光误判为命中才改为先定义事件。”
7. 重复转场：“总结一下，可读反馈不是越亮越好。”

| 全部单元 | 写作位置 | 必须保留的角色 | 预先规划而非已读证明 |
|---|---|---|---|
| 1、7 | 定义 | 结果辨认、强度边界 | 7可与1合并，但仍有独立裁决 |
| 2、6 | 方法与来由 | 步骤顺序、误判触发的改法 | 6不是可按人物经历随便删的背景 |
| 3、4 | 测试与限制 | fps、帧数、样本、未隔离通道、并发边界 | 跨章节同组阅读，禁止只读3 |
| 5 | 媒体 | 独立空间信息 | 可读则转录，否则留标且说明不能回答遮挡位置 |

## 自然段写作示例（媒体未读时不是完整通过样本）

```markdown
## 定义与方法
> 📍 原文：合成来源单元1、2、6、7。

作者将“可读反馈”定义为玩家能够辨认行动结果，而不是反馈越亮越好。这个界定来自旧版本的试玩经历：当时团队以美观为主，但试玩者会把无伤闪光误判为命中，因此作者改变了设计顺序。

方法是先确定玩家需要识别什么事件，再选择反馈通道，最后在竞争信息场景中验证。不能先堆特效，再倒推它要表达的事件。

## 测试结果与适用限制
> 📍 原文：合成来源单元3～5。

在同一台以60 fps运行的测试设备上，旧方案用6帧、新方案用3帧显示命中。参加测试的只有12名初次接触的玩家，其中7名说更容易辨认。测试没有隔离音效变化，因此不能单独归因于视觉方案。

这些结果也不能证明多目标同时命中时，并发信息仍然清楚；光敏条件尚未测试。原文另有一张远近目标遮挡关系图，未转录，具体空间位置不能由本文本确定。
```

这份 raw 记录作者定义、步骤、理由、观察和边界。若要提出“应该加并发验收”，放在阶段包的 AI 批注或后续 Wiki 推论，不放 Raw 尾部；不要混成作者已提出的规范。

## 七个高价值反例

| 错稿或错误裁决 | 原因 | 合格处置 |
|---|---|---|
| “反馈更亮所以更可读” | 定义反转；忽略后文条件 | required + distorted，修定义后重审 |
| “由6 ms缩短到3 ms” | 帧被换成毫秒，设备条件丢失 | required + distorted；保留6帧/3帧和60 fps；若换算注明推导，不能假装原文数值 |
| “新方案使辨认率提升58%” | 7/12自述不是提升率；无对照且未隔离音效 | required + distorted；保留观察与限制，不制造因果 |
| “试玩经历是背景可省略” | 误判经历解释设计顺序改变 | 6为required，缺失则missing；补回因果，不靠policy掩盖 |
| “图与正文同主题，已经覆盖” | 遮挡位置是独立图义 | 能读则转录；不能读则media + marker_only，整体为 media_limited，未留标为missing并阻断 |
| “最后重复一句，不是重要内容，因此已覆盖” | 是否必保与是否覆盖不同 | 若对应定义确实保留可complete；若严格重复省略用not_applicable + omit_duplicate并指明等价单元 |
| Wiki写“已证实所有场景有效” | 弱化作者限制且抹掉证据类型 | 保留单设备、初次接触、未隔离及并发未知；实测结果与推论分开 |

每单元按 v2 report 合同记录 policy、status 和要素级证据。required 仅完整无缺口可过；独立例子不能用 optional_supporting 豁免。逐条反查 Raw→source，并核对跨章节条件；位置和关键词匹配不能代替语义回读。

## Wiki 如何产生真实增量

设已有 Wiki 写：“反馈应让玩家知道行动是否生效。”新来源的增量是定义的强度边界、事件优先的步骤、无伤误判反例及测试外推限制；不是把一句旧话再贴一遍。

| 来源含义 | 已有页 | 本次动作 |
|---|---|---|
| 辨认结果 | 已覆盖 | 不重复扩写；不为增加来源数强行挂源 |
| 越亮不等于越可读 | 缺条件 | 在原定义后补限制和来源 |
| 先事件后通道、试玩误判来由 | 缺操作和因果 | 加入方法段，保持推导连贯 |
| 60 fps/6→3帧/7 of12 | 无同条件证据 | 加观察与未验证边界；不升为普遍阈值 |
| 假设另一独立来源主张高亮总有效 | 可能冲突 | 先核对并发/场景/判据，仍冲突时并列依据与缺口，不自动多数票 |
| 未读遮挡图 | 无可靠内容 | 保留raw媒体边界并挂账；不写Wiki空间结论 |

阶段三检查实际 diff 是否落实这些增量，章节来源和台账是否一致；未消费有理由和重开条件。新建/拆分只按真实知识边界与授权处理。

## 真正查用并闭合

对更新后的 Wiki 实际执行 Query：“反馈是否越亮越好；6帧和3帧说明什么？”核心 Wiki 全文读取，数字与因果回 raw。答案应说辨认结果是目标、该案例是有限条件下观察，不能把帧换毫秒或7/12写为因果提升；图片细节未知。工具读到文件只证明实际读取，不自动赋予答案正确性。

新运行使用 manifest + request + 独立 report + 真实 host 调用记录 + receipt；阶段一和回测使用同一个 raw-quality.mjs 核心。旧 v1/vNext 记录仅作历史解释。标准在阶段审核，自动中途保存回滚点后集中最终审核；两者都必须展示评分、raw内容、Wiki具体变化、拆分与回测结果。
