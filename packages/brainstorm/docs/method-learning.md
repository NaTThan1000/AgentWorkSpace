# 随任务进行方法学习

在宿主当前任务授权范围内：执行真实 Brainstorm 任务时，Agent 可从用户反馈、具体失败、多源研究和交付结果中发现改进，验证后维护本仓方法、案例及相应路由。没有增量不要求记录，不创建定时任务，也不修改全局个人偏好。

## 什么时候值得改

- 原方法存在可直接核对的事实、算术或来源错误。
- 点子持续抽象、同质化，或者没有吸收用户已给的反馈；能够指出具体失败与拟改变的操作。
- 新来源提供可迁移的认知机制，且存在当前方法没有覆盖的卡点。
- 交付或后续真实反馈改变了先前的适用判断。

仅“觉得应更专业”“新论文很流行”或一次用户偏好不足以加入默认方法。Brainstorm 学方法与共创；领域知识仍引用 Knowledge，专业分析仍按需使用 GAD，不复制知识库或专家体系。

## 最短完整处理

1. 读取具体问题、来源和当前目标文件；复用已知记录避免重复。
2. 写清拟改变的操作、适用任务和失效条件；外部事实按多源和时效要求查证。
3. 在当前授权范围内修正方法或案例，更新必要路由。权限、用户目标、质量标准、正式决定不是学习可修改对象。
4. 运行与改动匹配的验证，保留实际证据。确定性纠错可直接核验；新策略至少先作限定试用，不自动宣布普遍提升。
5. 使用 [method-learning.mjs](../scripts/method-learning.mjs) 保存可复核变更记录，绑定目标文件与证据哈希；记录工具不替 Agent 作语义审查，也不自动修改方法。
6. 新反例形成后续记录，引用 prior_id 并收窄或撤回适用范围。根据源文件与 Git 历史恢复，不能只写“withdrawn”却让默认路由继续使用被否定操作。

## 记录与使用范围

运行资格、证据与采用分开：

- trial：来源与操作足以在匹配任务中试用，效果尚未确立。
- scoped：有具体修正／运行证据支持当前明确范围，不能称普遍默认。
- withdrawn：有反例或失效条件，不再按原范围使用；更新实际方法／路由后记录。

每条记录包含 id、kind、trigger、source_refs、scope、disposition、targets（相对路径及 SHA256）、evidence（文件、SHA256、结果与实际验证说明）、limitations；后续修改有 prior_id。不得用全局、所有任务或所有模型作为无边界 scope。

记录文件保存在 docs/learning-records，不是第二份方法正文或长期知识库。相同内容重复 record 为 no-op，同 ID 不同内容拒绝，修订使用新 ID 和 prior_id。旧证据和失败不覆盖。

targets 只允许 methods、perspectives、examples/co-creation；工具不允许写 session、GAD、Knowledge、权限配置或全局记忆。需要修改运行代码来修 bug 时作为普通框架维护处理，不伪装成内容学习。

## CLI

从 Brainstorm 根目录执行：

    node scripts/method-learning.mjs validate --input path/to/record.json
    node scripts/method-learning.mjs record --input path/to/record.json

validate 检查字段、目标与证据真实存在且哈希一致、链引用与路径边界。record 写不可覆盖的记录；没有实际目标修改／证据不能以 scoped 代替尚未验证的假设。输出 structure_passed 仅表示这些检查，semantic_review_required 始终为 true。

使用 Agent 判断证据是否匹配声明，不能将脚本通过当效果已证明；是否激发用户仍来自真人反馈。

## 有用的正反例

- 正例：6-3-5 文本轮次和总数矛盾。核对步骤、复算，再同步操作说明和案例数字；仅声明算术／表述修正，不声称新方法提高创造力。
- 正例：用户理解候选但没有兴趣，旧步骤却继续补解释。试用“改发散轴并保留已喜欢片段”，记录所测场景；新的反例若显示是未理解而非没兴趣，应收窄条件。
- 反例：用户说本项目不喜欢时间轴，就把所有未来任务都改成空间玩法，或自动写入个人画像。
- 反例：把候选高分、多个 persona 一致或新文档完整当成通用效果；把 Knowledge 查询材料复制进本仓作为新的权威。
- 反例：记录 withdrawn 但没有调整对应方法／默认路由，或修改了目标后继续复用不匹配哈希的旧证据。
