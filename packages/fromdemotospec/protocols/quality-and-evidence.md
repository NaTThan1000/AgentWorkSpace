# 质量与证据 · v2

本协议拥有 V1、90+ 的语义条件。工具只核对声明和可访问证据，不能判断游戏好玩、替用户作决定，或证明没有未知 Bug。

## 阶段判定

| 结果 | 必要条件 | 不能用来替代的证据 |
|---|---|---|
| 内部构建 | 已实际形成的内容如实标明缺口 | 编译成功不称 V1 |
| V1（约80） | 承诺的完整闭环可达；功能与异常路径实现；能开始、理解、操作、结束／重开；必要表现反馈到位；已知 Bug 清零；约定环境实际运行；设计与证据可恢复 | 文档齐全、模拟数量、截图或平均分不能抵消任一缺项 |
| 90+ | V1 底线持续满足；用户本人认可当前核心玩法；约定的主要体验问题关闭；组合行为和受影响部分复验；工程交接准备就绪 | Agent 评分、其他测试者赞同或用户仅认可美术都不能替代核心玩法认可 |
| 原型交付 | 90+ 加上[路径接收条件](handoff-and-production.md) | 技术通过不等于接收完成，更不等于发布 |

V1 可在用户首次试玩前由 Agent 根据实际证据声明；用户仍可发现内部检查遗漏。90+ 的用户认可必要但不充分。实际接收属于交付环节，不与90+互设循环前提。

## 六个不可相互抵消的检查面

| 检查面 | V1 必须能证明 | 迭代重点 |
|---|---|---|
| 范围与功能 | 承诺项及失败／边界行为可达，核心系统之间有闭环 | 组合稳定性、取舍验证 |
| 核心体验 | 关键选择有代价与可经历的后果；玩家可见目标有实际可达路径；按风险检查无代价固定答案 | 用户认可、主要体验问题关闭与策略空间复核 |
| 操作与理解 | 首次进入能知道目标、可做行动和当前状态，失误可解释、可重开 | 信息负担、节奏及学习过程 |
| 表现与反馈 | 理解、感受、整体一致性均有检查；前中后反馈完整 | 因果、力度、音画、强调和干扰 |
| 可靠性 | 约定环境与关键场景实际运行，已知 Bug 清零 | 实际发现的问题有回归覆盖 |
| 工程与追溯 | 构建／启动可重复，规则、决定、实现、证据可定位 | 接手准备、债务处置与可维护性 |

不要求所有品类相同的测试数、模拟局数、帧率指标或画面数量。项目按目标设备和风险预先明确必要检查与可接受范围。

## 证据必须对应实际对象

每条记录包含：ID、问题或验收场景、构建版本／提交或内容哈希、环境、前提及输入、预期与实际结果、方法、产物引用、执行者和限制。失败证据保留，并连接修复与复验；不能覆盖失败只留 PASS。

按风险组合使用规则／边界测试、真实目标环境输入、完整闭环游玩、静态画面、动效时序、音频与必要性能记录。模拟适合规则和大量组合；截图适合布局与状态；静态画面不能证明动效、听感或可操作。浏览器启动、真实按键与运行日志不能由纯模型推演冒充。无法运行必要环境时标明缺口，不能声明该环境通过。

## 目标可达与反策略检查

玩家可见的胜利、评级、挑战或奖励目标，必须区分“满足条件后判定正确”和“从正常初态经合法输入实际可达”。边界夹具、状态注入或直接调用适合验证判定规则，不能单独证明完整路径存在；目标尚未实际达成时可以交付为待验证挑战，但必须明确范围，不能声称可解或用降低目标换取测试通过。

随机化或内容变体还要区分配置预算、结构不变量和玩家实际难度。数量、生命、距离或拓扑相同，只能证明这些变量被控制；若玩家能力、历史占位、先后状态或信息条件不随之对称，不能据此宣称实际同难。按目标需要选代表性变体试玩或模拟，并保留未覆盖范围。

内部体验检查根据已识别风险尝试少量反策略：绕开目标、无代价拖延、资源无限累积、单一动作／角色包办、末段失去决策等。目的是发现明显支配策略和系统失效，不要求穷举全部最优解，也不以Agent未发现漏洞证明平衡成立。发现后区分实现Bug、体验问题与新设计机会，再决定修复或交用户判断。

复用输入未变且覆盖仍有效的结果。影响分析至少指出改了什么、哪些场景／认可会失效、为何其他证据仍有效。不得为了降低成本继续引用已失效证据；无需每次重跑所有无关检查。

## 用户认可记录

保留用户原话或忠实摘录、会话／项目决定引用、日期、对应构建与范围，以及 Agent 对适用范围的解释。只有实际表达核心玩法认可才能记录为认可；“画面合适”“测试通过”“可以继续”不能自动扩张为此含义。不把测试夹具当真实用户记录。

核心循环、关键选择或后果发生实质变化时重新取得覆盖新范围的认可。普通修复／局部表现调整可在有影响说明与回归证据时沿用仍有效的认可，不逐次打断用户。认可来源不清时保持 pending，准备具体构建让用户集中判断。

## 问题分类与关闭

Bug 是可复现的承诺行为偏差，包括错误信息、输入失效、状态损坏及阻碍判断的表现错误。优先修启动／崩溃／卡死，再规则与信息，再其他缺陷；优先级不降低 V1 的已知 Bug 清零要求。

体验问题与偏好、新需求、假设和技术债分别记录。不能把 Bug 改名成偏好、静默修改预期或缩范围来消除门禁。问题关闭需原因、实际修复及相关复验引用；接受一项债务不等于缺陷已修复。

执行结果应同时报告：实际达到的阶段、覆盖环境与场景、未覆盖和未知、用户认可状态、路径交付状态。工具 PASS 永远只代表该工具实际核对的合同。
