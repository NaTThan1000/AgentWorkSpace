# 已填示例 · 可持续空间经营工程

**本例完全虚构，用于展示工程选择、贯通设计、接收和正式切片。没有创建或验证引擎工程。** 技术版本仅是示例输入约束，不构成选型推荐。

## 项目入口与制作定义

名称：浮岛工坊。路径：maintained-project；原因是后续将保留经营逻辑、建筑表现与交互，在同一工程增加生产链。示例环境约束：Windows桌面，Godot4.4.1，GDScript，鼠标／键盘，离线单人，不联网；无存档需求的首个原型不提前实现存档。实际工程与构建命令尚未运行，阶段internal／工程选型已描述。

体验目标：玩家通过有限空间安排生产与运输，在产出和拥堵间取舍。闭环：放置建筑→投入原料→运输／生产→获得资金→改造布局→下一轮供给。验证深度需经历布局变化前后与产能扩张，内容限制为两种建筑、一种原料、一个订单循环；不做大型科技树或随机地图。

示例执行方法：按目标引擎建立可运行空场景、输入与状态显示后，实现完整订单切片。实际使用时把依赖安装、导入、运行和构建操作核对写入入口；不能只因本例列了引擎就声称初始化通过。

## 设计与工程边界

| 职责 | 有效规则／输入 | 表现和验证 |
|---|---|---|
| 网格与占用 | 同一格不可重复占用，撤销只退回已提交的本次操作 | 合法／冲突预览与放置响应一致；边缘和快速连点检查 |
| 生产规则 | 原料到达后开始处理，完成后交付订单；单位与计时由数据源拥有 | 建筑状态、进度与产出时刻对应；不能靠动画完成回调决定规则真值 |
| 运输 | 按实际路径到达，阻塞可解释且可恢复 | 方向、堵点与资源归属可见；布局修改时不重复发货 |
| UI与诊断 | UI发送明确命令，诊断读同一状态 | 玩家聚焦建设；按需查看物流事件而不常驻全量调试面板 |

A-01：Agent 假设，两种建筑已足以形成空间取舍。R-01：局部流畅但整体可能长期堵塞，需跨系统完整循环证据。用户决定与核心玩法认可均为pending，本例没有accepted记录。

## 表现与证据

代表性片段必须同时出现建筑预览、放置、开始生产、运输堵塞与订单完成。约束：建筑轮廓可区分，物流方向与拥堵有冗余线索，订单完成有适当节奏和力度；不以堆资产表达完成度。

计划按实际输入、完整订单、布局修改、极端拥堵和重开检查；静态图只覆盖布局，动态反馈需运行。所有结果not-run，尚无构建、截图、音频或性能事实。

## 接收与正式开发

到90+仍需真实用户核心玩法认可和其他质量条件。随后接收 Agent 从交付版本恢复依赖并构建，实际运行订单循环，完成真实小改动“添加订单完成提示强度设置”，核对设置存续与原订单流程回归，记录差异及证据。此处只是接收任务设定，未执行，handoff=not-started。

正式下一切片：增加第二类订单。先检查订单数据边界是否足够；若只需扩数据则不重搭架构。切片包含新订单条件、目标提示、结算反馈、原订单回归和存档需求评估。新增联网、商店发布或付费资产不属于此授权。

恢复原则：保留最后可运行工程、底稿、资源来源和证据；针对阻碍当前切片的债务局部重构。下一动作是按示例环境建立真实可运行起点，而不是生成一套假定已验证的通用引擎模板。
